
# DGC-0001 — Dharma Governance Charter

**Document ID:** DGC-0001
**Founder:** Paresh Somani
**Version:** 1.0
**Status:** Founding Freeze

> Defines how the Dharma Protocol is governed, how specifications evolve, and how amendments are accepted while preserving Principle 0.

---

# Abstract

The Dharma Governance Charter establishes the constitutional process by which Dharma specifications evolve.

Its purpose is to preserve stability without preventing improvement.

Governance applies to the protocol—not to ownership of any future company.

---

# 1. Foundational Principle

Every governance decision MUST remain compatible with:

> Principle 0: Capability does not constitute authority.

No amendment may contradict Principle 0.

---

# 2. Governance Objectives

Governance exists to:

- preserve protocol stability,
- prevent conflicting specifications,
- provide predictable amendment procedures,
- protect historical records,
- allow future evolution.

---

# 3. Governance Layers

The Dharma ecosystem contains three governance layers.

| Layer | Responsibility |
|--------|----------------|
| Constitutional | Immutable principles |
| Standards | RFC evolution |
| Implementation | Software behavior |

Constitutional decisions are the highest authority.

---

# 4. Founder Role

The Founder establishes the initial constitutional foundation.

Initial Founder:

**Paresh Somani**

Founder responsibilities include:

- preserving constitutional continuity,
- approving Founding Freeze releases,
- recording Founder Ledger decisions.

The Founder does not rewrite history.

Historical documents remain permanent.

---

# 5. Protocol Council

Future governance introduces a Protocol Council.

Purpose:

Technical stewardship.

The Council may:

- review RFCs,
- recommend amendments,
- publish implementation guidance,
- maintain registries.

The Council may not violate Principle 0.

---

# 6. Amendment Classes

Not every change is equally important.

## Class A — Constitutional

Examples:

- Principle 0
- Constitutional Articles

Requirements:

Highest approval threshold.

## Class B — Protocol

Examples:

- DAP
- Packet Modes
- Validation Rules

Requires formal review.

## Class C — Registry

Examples:

- Error codes
- Reserved identifiers

Administrative process.

## Class D — Editorial

Examples:

- spelling,
- formatting,
- clarification.

No behavioral change.

---

# 7. Amendment Lifecycle

Every amendment follows one lifecycle.

PROPOSE

↓

DISCUSS

↓

REVIEW

↓

DECIDE

↓

PUBLISH

↓

ARCHIVE

Every stage becomes permanently recorded.

---

# 8. Proposal Format

Every proposal receives a unique identifier.

Example:

DGP-0001

Required fields:

- Title
- Author
- Motivation
- Specification
- Compatibility Analysis
- Impact

No anonymous constitutional amendments.

---

# 9. Compatibility Review

Every proposal MUST answer:

1. Does it preserve Principle 0?
2. Does it preserve Compatibility Before Replacement?
3. Does it break existing implementations?
4. Can older implementations safely ignore it?

If compatibility fails, the proposal fails.

---

# 10. Decision Matrix

| Amendment | Decision Path |
|-----------|---------------|
| Constitutional | Founder + Constitutional Process |
| Protocol | Protocol Council Review |
| Registry | Registry Maintenance |
| Editorial | Administrative Update |

Different changes follow different authority paths.

---

# 11. Founder Ledger

Major historical decisions receive permanent ledger entries.

Examples:

- DL-0000 Founding Freeze
- DL-0001 Principle 0
- DL-0002 Open Protocol

Ledger entries are immutable historical records.

---

# 12. Version Policy

Specifications evolve through version numbers.

Examples:

DRFC-0002 v1.0

↓

v1.1

↓

v2.0

Historical versions remain accessible.

No published version is erased.

---

# 13. Supersession

A newer specification may supersede an older one.

Example:

DRFC-0006

Supersedes

DRFC-0003

The older document remains archived.

Superseded does not mean deleted.

---

# 14. Emergency Process

Critical protocol failures require expedited governance.

Emergency conditions include:

- security failure,
- validation inconsistency,
- protocol ambiguity.

Emergency updates receive permanent historical records.

---

# 15. Registry Stewardship

DPR-0001 remains the official registry.

New permanent identifiers require registration before publication.

Duplicate permanent identifiers are prohibited.

---

# 16. Public Review

Future public RFCs may enter community review.

Community feedback may:

- identify flaws,
- improve wording,
- suggest extensions.

Community feedback alone does not automatically change the protocol.

---

# 17. Governance Integrity Rules

The governance system itself follows six permanent rules.

1. History remains permanent.
2. Principle 0 remains immutable.
3. Compatibility is reviewed before adoption.
4. Every amendment is traceable.
5. Registries prevent collisions.
6. Governance decisions produce evidence.

These rules preserve institutional continuity.

---

# 18. Worked Example

Proposal:

Add a new packet mode.

Process:

- DGP-0042 submitted.
- Compatibility review completed.
- Protocol Council recommends approval.
- Registry assigns a permanent mode value.
- New RFC published.
- Previous versions archived.

The protocol evolves without rewriting history.
